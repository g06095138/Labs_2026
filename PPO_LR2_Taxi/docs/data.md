# ЛР2. Логическая модель данных финансового модуля такси
Сохраняются исходный финансовый план и его три месяца. Выручка, прибыль, поступления, задолженность, прогнозные деньги, потребность в финансировании и сравнение вычисляются при запросе и отдельными таблицами не хранятся.

## 1. Сущности и поля
### `Plan` — финансовый план службы такси
| Поле | Назначение |
|---|---|
| `Id` **PK** | Постоянный непустой UUID, сохраняется при изменении плана. |
| `Name` | Непустое после trim название, до 200 символов. Разные планы могут иметь одинаковое название; идентичность определяется Id. |
| `InitialCash` | Начальные деньги перед месяцем 1, ≥0, точность копейки. |

Plan — сохраняемое представление FinancialPlan из Domain. Его расчёт не меняет оперативные заказы такси.

### `MonthPlan` — параметры месяца плана
| Поле | Назначение |
|---|---|
| `PlanId` **PK, FK → Plan.Id** | Владелец набора параметров, часть составного ключа. |
| `Number` **PK** | 1, 2 или 3, вторая часть ключа; номер уникален внутри плана. |
| `Quantity` | Q — целое число выполненных и проданных поездок, 0…1000000. |
| `Price` | P — средняя плановая цена поездки, неотрицательная, до копейки. |
| `VariableCost` | V — переменные затраты на поездку, неотрицательные, до копейки. |
| `FixedCost` | F — постоянные расходы месяца, неотрицательные, до копейки. |
| `PaymentPercent` | A — целый процент оплаты текущих поездок в текущем месяце: 0…100. |

Денежные входы ограничены 10^12 руб. для безопасного decimal-расчёта в ЛР3. Months в FinancialPlan представлены неизменяемыми MonthParameters; PlanId при отображении в хранилище определяется содержащим планом. Отдельный искусственный MonthId не нужен.

## 2. Связи и кратности
| Связь | Кратность | Внешний ключ |
|---|---|---|
| `Plan` → `MonthPlan` | `1 : 3` | `MonthPlan.PlanId` |

Каждый MonthPlan принадлежит ровно одному Plan. Составной **PK(PlanId,Number)** одновременно обеспечивает уникальность номера в плане. Одного PK/FK недостаточно, чтобы в каждом плане были именно три записи: полный набор {1,2,3} должен проверяться Application и сохраняться атомарно.

Логическая ER-диаграмма в нотации Чена: [er.svg](diagrams/er.svg), исходник [er.puml](diagrams/er.puml). Связь не обозначается M:N: один и тот же набор параметров не делится между планами.

### 2.1. Обозначения нотации Чена
Сущность «Финансовый план» — прямоугольник; её атрибуты — овалы, Id подчёркнут сплошной линией. «Месяц плана» — слабая сущность с двойным прямоугольником: у неё нет самостоятельного глобального идентификатора. Номер месяца Number подчёркнут пунктиром как частичный ключ, уникальный только в пределах плана.

«Содержит» — идентифицирующая связь с двойным ромбом. Она вместе с ключом плана определяет месяц. Двойные линии показывают обязательное участие; кратность 1:N дополнена бизнес-ограничением: у каждого плана ровно три месяца с номерами 1,2,3.

На концептуальной диаграмме PlanId не дублируется отдельным овалом у месяца: принадлежность задаётся связью. При отображении в таблицы ключ месяца остаётся (PlanId,Number), как описано выше. Вычисляемые отчёты не добавляются к сохраняемым сущностям.

## 3. Правила сохранения и целостности
1. **Проверка.** Id плана непустой и уникальный; имя непустое; все входы соответствуют П-Б8–П-Б10. Суммы сохраняются без потери копеек, вычисления выполняются в decimal; float/double для денег не используются.
2. **Первое сохранение.** Plan и ровно три MonthPlan создаются в одной транзакции. Ошибка или отмена не оставляет неполный план.
3. **Повторное сохранение.** Тот же Id обновляет исходные поля и все месяцы без дубликатов. Другой план не меняется; совпадение названий не объединяет планы.
4. **Восстановление.** После перезапуска открывается тот же Id, Name, InitialCash и все месячные входы. Отчёта до команды расчёта нет. Новый Forecast из исходных денег и долга 0 воспроизводит прежние показатели.
5. **Ошибки.** Повреждённый набор месяцев не открывается частично. Сбой сохранения оставляет предыдущую версию целой. Отсутствующий Id отличается от недоступности БД.
6. **Вычисляемые значения.** ClosingCash и ClosingDebt переносятся между месяцами в памяти при Forecast; их не нужно сохранять как исходные MonthPlan. D3 не превращается автоматически в деньги.
7. **Доступ и интеграция.** Основной участник — руководитель службы. Авторизация будущего финансового веб-экрана проектируется в ЛР5; здесь не вводятся новые пользователи/пароли или таблицы доступа. Существующая авторизация сайта не изменяется.

Это логическая модель ЛР2: конкретные SQL-типы, индексы и создание физической SQLite-схемы относятся к ЛР4. Реальный SqlitePlanRepository финансовых планов ещё не реализован. Действующие Clients/Drivers/Tariffs/Orders сайта не подменяют финансовые Plan/MonthPlan.
