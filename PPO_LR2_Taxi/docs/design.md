# ЛР2. Проектирование финансового модуля службы такси

## 1. Архитектура
Приложение использует четыре слоя. Финансовые формулы не зависят от интерфейса и БД. Предполагаемый стек сайта: C#, .NET 10, Blazor Web App, SQLite, xUnit. Консоль ЛР3 — временный UI-адаптер.

| Слой | Ответственность | Зависимости |
|---|---|---|
| **UI** (`TaxiFinance.Web`, проект ЛР5) | Ввод/редактирование трёх месяцев, результат прогноза, выбор и сравнение планов, сообщения; открытие сохранённых входов. | Application; Infrastructure только в composition root для DI |
| **Application** (`TaxiFinance.Application`) | ForecastService, ComparisonService; последовательность сценариев; интерфейс IPlanRepository. | Domain |
| **Domain** (`TaxiFinance.Domain`) | FinancialPlan, MonthParameters, PlanValidator, FinancialCalculator, отчёты и итоги. | Не зависит от других слоёв |
| **Infrastructure** (`TaxiFinance.Infrastructure`, проект ЛР4) | SqlitePlanRepository: реализация IPlanRepository; схема, точное сохранение входов и транзакции. | Application, Domain |

UI вызывает Application. Реализация хранилища подключается через DI. Финансовое ядро и консоль ЛР3 уже существуют отдельно; SQLite и финансовый Blazor UI остаются проектом. Операционный сайт заказов не меняется. Схема компонентов: [components.svg](diagrams/components.svg), исходник [components.puml](diagrams/components.puml).

## 2. Основные классы
| Классы | Назначение |
|---|---|
| FinancialPlan | Постоянные Id, Name, InitialCash и три набора месячных параметров. |
| MonthParameters | Номер 1–3, Quantity, Price, VariableCost, FixedCost, PaymentPercent. |
| PlanValidator | Проверка всего плана до вычисления месяца 1. |
| FinancialCalculator | Чистый расчёт одного месяца и итоговых показателей. |
| MonthReport, FinancialSummary | Вычисляемые показатели месяца и итоги трёх месяцев. |
| PlanForecast | Id/название, три отчёта и итог. |
| ForecastService | Последовательность трёх расчётов с переносом денег и долга. |
| ComparisonService, PlanComparison, ComparisonSide | Сравнение двух независимых планов, каждый со своими четырьмя итогами. |
| IPlanRepository, SqlitePlanRepository | Контракт будущего хранилища и проект его реализации в Infrastructure. |

FinancialPlan содержит ровно три MonthParameters, PlanForecast — ровно три MonthReport и один FinancialSummary. PlanComparison содержит две ComparisonSide, каждая имеет один FinancialSummary. Вычисляемые результаты не являются таблицами хранения.

Модели входа и результата неизменяемы. FinancialPlan копирует коллекцию входных месяцев; ForecastService сортирует новую последовательность и не меняет исходный порядок. Диаграмма классов: [domain.svg](diagrams/domain.svg), [domain.puml](diagrams/domain.puml). Данные и ключи: [data.md](data.md).

## 3. Правила расчёта
Все финансовые операции — decimal, валюта RUB. Единая плановая услуга — поездка; Q — количество, P — средняя цена, V — переменные затраты на одну поездку, F — постоянные расходы, A — целый процент текущей оплаты.

```text
R = Q × P
VariableExpenses = Q × V
ContributionMargin = R − VariableExpenses
E = VariableExpenses + F
Profit = R − E
S = Round(R × A / 100, 2, AwayFromZero)
D = R − S
Receipts = S + OpeningDebt
C = OpeningCash + Receipts − E
TotalProfit = Profit1 + Profit2 + Profit3
RequiredFinancing = max(0, −min(C1, C2, C3))
```

Месяц 1: OpeningCash=InitialCash, OpeningDebt=0. Следующий месяц получает ClosingCash и ClosingDebt предыдущего. Каждый Forecast начинает заново; накопление от прошлого вызова запрещено. Отрицательный расчётный C допустим: показывается дефицит, прогноз продолжается. При C=0 дефицита нет. D3 остаётся задолженностью, не добавляется к C3; четвёртого месяца нет.

Проверка: Guid не пустой; имя после trim не пустое, длина ≤200; ровно месяцы 1,2,3 без повторов; Q — int 0…1000000; A — int 0…100; InitialCash/P/V/F — 0…10^12 руб. и точность до копейки. Эти технические пределы согласованы с кодом ЛР3 и защищают диапазон decimal. Они относятся к входам; переносимый отрицательный C ими не запрещается. P<V допустимо. Поля проверяются для всех месяцев до начала расчёта.

## 4. Контракты прикладных операций
Общий отказ в расчётном коде: FinanceValidationException с Field и Message. Будущий UI показывает поле и причину; внутренние детали БД не выводятся. Для UI ниже даны проектные имена операций сохранения/открытия: в ЛР3 существует только их интерфейс IPlanRepository, реализованных SQLite-операций ещё нет.

| Операция | Вход | Результат | Основные ошибки |
|---|---|---|---|
| **ForecastService.Forecast** | FinancialPlan с начальными деньгами и тремя месяцами. | PlanForecast: месячные показатели, прибыль, C3, D3 и финансирование. Только вычисление. | Неверные Id/Name/InitialCash/Months/поле месяца; числовая ошибка. Весь прогноз отклоняется, частичный не выдаётся. |
| **ComparisonService.Compare** | Два допустимых плана с разными Id. | PlanComparison: имена/Id и независимые итоги обеих сторон. Только вычисление. | Одинаковый Id; неверный левый/правый план с префиксом Left/Right в Field. |
| **SavePlan → SaveAsync** (проект) | Полный допустимый FinancialPlan, сигнал отмены. | Подтверждение атомарного сохранения плана и трёх месяцев. Тот же Id обновляет, другой план не меняется. | Ошибка валидации; недоступное хранилище; отмена/сбой записи — прежняя версия цела. |
| **ListPlans → ListAsync** (проект) | Сигнал отмены. | PlanListItem(Id,Name) для всех сохранённых планов; сортировка Name ordinal, затем Id. Пустое хранилище → пустой список. | Ошибка чтения или отмена не подменяется пустым списком. |
| **OpenPlan → LoadAsync** (проект) | Непустой planId, сигнал отмены. | Сохранённый план с тремя исходными месяцами; прогноз выполняется отдельно. LoadAsync возвращает null при отсутствии; Application преобразует его в «План не найден». | Неверный Id; отсутствующий план; повреждённые данные; ошибка чтения/отмена. Частичный план не открывается. |

**Контракт пересчёта.** Forecast читает только исходные месяцы. На каждой из трёх итераций переносит C и D; не прибавляет задолженность дважды. Финансирование — максимум месячных дефицитов, а не сумма. Compare рассчитывает обе стороны заново, не разделяет между ними начальные деньги/долг и не изменяет входы.

**Актуальность UI.** После изменения имени или любого входного параметра будущий UI скрывает прежний прогноз и сравнение с ним до пересчёта. Чистые сервисы ЛР3 не кешируют результаты, поэтому отдельного состояния актуальности в них нет. Финансовый UI реализуется в ЛР5.

**Сохранение и открытие.** Прикладной слой валидирует план до записи. План и три месяца сохраняются одной транзакцией. При отмене/сбое прежние данные не повреждаются. После открытия загружаются только входы, затем пользователь запускает Forecast. Параметры плановых цен не связаны FK с оперативными тарифами сайта, поэтому смена текущего тарифа не меняет сохранённый план.

## 5. Обоснование решений
**SRP.** FinancialCalculator отвечает за формулы; ForecastService — за три шага и перенос состояния; ComparisonService — за две независимые альтернативы; UI/Console — за ввод и представление. Изменение экрана не меняет формулы. Один калькулятор используется в прогнозе, сравнении и тестах.

**DIP.** IPlanRepository объявлен в Application. Будущий SqlitePlanRepository в Infrastructure реализует контракт; Application не зависит от Microsoft.Data.Sqlite или пути БД. Замена способа хранения и тестовая реализация не требуют изменения Domain. Domain не зависит даже от интерфейса хранилища.

## 6. Ручная проверка трёх последовательных месяцев
Начальные деньги 50000 руб. В каждом месяце Q=500, P=300, V=100, F=70000, A=50%. Это контроль такси из ЛР1, эквивалентный денежным суммам исходного задания.

R=150000; переменные расходы=50000; маржинальный доход=100000; E=120000; прибыль=30000; S=75000; D=75000.

| Месяц | Начальные деньги | Начальный долг | S | Поступления | Расходы | Конечные деньги | Конечный долг | Прибыль |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 50000 | 0 | 75000 | 75000 | 120000 | 5000 | 75000 | 30000 |
| 2 | 5000 | 75000 | 75000 | 150000 | 120000 | 35000 | 75000 | 30000 |
| 3 | 35000 | 75000 | 75000 | 150000 | 120000 | 65000 | 75000 | 30000 |

М1: 50000+75000−120000=5000. М2: 5000+75000+75000−120000=35000. М3: 35000+75000+75000−120000=65000.

Итоги: прибыль=90000; деньги C3=65000; долг D3=75000; финансирование=0. Повторный расчёт воспроизводит результат и не меняет план. Для сравнения вариант A=0% даёт ту же прибыль 90000, но C3=−10000, D3=150000 и финансирование 70000. Так проверяется отличие прибыли от наличия денег.
