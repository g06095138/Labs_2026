# Проектирование. ЛР3 — оператор связи

## 1. Разделение ответственности

| Часть | Ответственность | Зависимости |
|---|---|---|
| `TelecomFinance.Domain` | Входная модель, валидация, формулы месяца и итогов, типы результатов | Без зависимостей от Application, консоли и БД |
| `TelecomFinance.Application` | Последовательность прогноза и независимое сравнение; контракт будущего хранилища | Только Domain |
| `TelecomFinance.Console` | Команды demo/forecast/compare, чтение JSON и форматирование | Application и типы Domain |
| Infrastructure, будущий этап | Сохранение исходных параметров через контракт Application | Реализация в ЛР4 |
| Blazor UI, будущий этап | Редактирование, результат и сравнение | Прикладные операции в ЛР5 |

Диаграмма классов: [domain.svg](diagrams/domain.svg), редактируемый исходник `docs/diagrams/domain.puml`. Параметры месяца — неизменяемые записи, план копирует входной список в коллекцию только для чтения. Результаты не записываются обратно в план.

**SRP:** формула не зависит от способа показа. Консоль можно заменить веб-экраном, сохранив расчёт. **DIP:** будущее хранилище подключается через контракт Application; расчёт не зависит от SQLite/PostgreSQL и SQL-запросов.

## 2. Объекты

- `FinancialPlan`: UUID, название, начальные деньги, начало календаря, три `MonthParameters`.
- `MonthParameters`: номер, количество клиентов, средние оплачиваемые минуты, цена минуты, абонплата, переменные затраты на клиента, постоянные расходы, процент оплаты.
- `MonthReport`: начальные деньги и долг; выручка, переменные расходы, маржинальный доход, все расходы, прибыль, текущая оплата, поступления, конечные деньги и долг; признак дефицита. Дополнительно показаны `BillableMinutes`, `CallRevenue`, `SubscriptionRevenue` — общий объём оплачиваемых минут и две составляющие выручки.
- `FinancialSummary`: общая прибыль, конечные деньги, долг после третьего месяца, требуемое начальное финансирование.
- `PlanForecast`: идентификатор/название плана, календарное начало `StartPeriod`, три отчёта, итог.
- `PlanComparison` и `ComparisonSide`: итоги левого и правого планов без общего изменяемого состояния.
- `FinanceValidationException`: поле `Field` и понятная причина ошибки.

Календарь месяца вычисляется из старта плана и номера 1/2/3. Он не меняет денежные формулы. Финансовый год всех трёх периодов должен оставаться в диапазоне 2020…2099.

## 3. Формулы Domain

P = средние оплачиваемые минуты × цена минуты + абонплата. Q — клиенты, V — затраты на клиента, F — постоянные расходы, A — процент оплаты.

```text
R = Q × P
VariableExpenses = Q × V
ContributionMargin = R − VariableExpenses
E = VariableExpenses + F
Profit = R − E
S = Round(R × A / 100, 2, AwayFromZero)
D = R − S
Receipts = S + OpeningDebt
C = OpeningCash + Receipts − E
TotalProfit = Profit1 + Profit2 + Profit3
RequiredFinancing = max(0, −min(C1, C2, C3))
```

Для исходных денег, цены и расходов запрещены отрицательные значения; для перенесённого `OpeningCash` отрицательное значение допустимо. Округляется оплата, а долг получается вычитанием. Промежуточные расчёты выполняются в decimal. Четвёртый месяц и автоматическое заимствование не добавляются.

## 4. Контракты операций

### `PlanValidator.Validate(plan)`

**Вход:** план целиком. **Успех:** план соответствует всем ограничениям спецификации. **Ошибка:** `FinanceValidationException` с полем и причиной; проверяются UUID, имя, C0, календарь и все три месяца. Ошибка третьего месяца должна быть найдена до выдачи прогноза.

### `FinancialCalculator.CalculateMonth(month, openingCash, openingDebt)`

**Вход:** допустимый месяц, начальные деньги (в том числе перенесённые отрицательные), неотрицательный начальный долг. **Результат:** новый отчёт по формулам раздела 3. **Ошибка:** недопустимый параметр или невозможность денежного расчёта. Изменения объектов и банковские операции отсутствуют.

### `ForecastService.Forecast(plan)`

**Вход:** полный план. **Действие:** проверить весь план; задать `cash = InitialCash`, `debt = 0`; обойти месяцы по номеру 1/2/3. После `CalculateMonth` передать `ClosingCash` и `ClosingDebt` следующей итерации. Сформировать итог через `FinancialCalculator.Summarize`.

**Результат:** новый `PlanForecast`. **Ошибка:** невалидный план или расчёт; частичный прогноз не публикуется. Каждый вызов начинает расчёт заново. Входные месяцы, их порядок в исходной коллекции и результаты прошлых вызовов не меняются.

### `ComparisonService.Compare(left, right)`

**Вход:** два полных плана с разными UUID. **Действие:** проверить обе стороны до расчётов и независимо вызвать прогноз для каждой. **Результат:** две стороны с итоговой прибылью, C3, D3 и финансированием. **Ошибка:** `Left.…`/`Right.…` и причина либо одинаковые UUID; никакая сторона не изменяется.

### Будущие операции хранения

**Сохранить:** вход — полный допустимый план; результат ЛР4 — атомарно записанный план и три месяца, повторный UUID обновляет запись; ошибки — валидация/хранилище.

**Список:** вход — запрос списка; результат ЛР4 — идентификаторы и названия; ошибка — хранилище.

**Открыть:** вход — UUID; результат ЛР4 — те же исходные значения или отсутствие плана; ошибка — хранилище/повреждённые данные. После открытия прогноз рассчитывается заново. В ЛР3 постоянное хранилище не реализовано; JSON — вход консоли.

## 5. Консоль

`demo` или отсутствие аргументов запускает контрольные 0/50/100% и сравнение 0% с 50%. `forecast <файл.json>` рассчитывает один план; `compare <левый.json> <правый.json>` сравнивает два. Валидационная ошибка выводит поле и причину, а процесс завершается с ненулевым кодом. Формулы в форматировании не дублируются.

`Program.cs` отвечает за запуск и отображение, `PlanInput.cs` — за десериализацию. JSON не допускает неизвестные/повторные свойства и пропущенные обязательные параметры; целые поля не принимают дробь. Неоплаченный остаток выводится отдельно от денег; при отрицательном денежном остатке используется подпись «Не хватает денег».

## 6. Ручной проход трёх месяцев при A = 50%

Начало — ноябрь 2026, C0 = 50000, D0 = 0. Каждый месяц: 100 клиентов × (200 минут × 5 ₽ + 500 ₽ абонплаты). R = 150000; переменные расходы = 100 × 500 = 50000; маржинальный доход = 100000; E = 50000 + 70000 = 120000; прибыль = 30000; S = 75000.

| Показатель | Ноябрь 2026 | Декабрь 2026 | Январь 2027 |
|---|---:|---:|---:|
| Начальные деньги | 50000 | 5000 | 35000 |
| Начальный долг | 0 | 75000 | 75000 |
| Выручка | 150000 | 150000 | 150000 |
| Маржинальный доход | 100000 | 100000 | 100000 |
| Все расходы | 120000 | 120000 | 120000 |
| Прибыль | 30000 | 30000 | 30000 |
| Оплата текущих счетов | 75000 | 75000 | 75000 |
| Поступления | 75000 | 150000 | 150000 |
| Конечные деньги | 5000 | 35000 | 65000 |
| Конечный долг | 75000 | 75000 | 75000 |

Общая прибыль = 90000; конечные деньги = 65000; конечный долг = 75000; финансирование = 0. Долг третьего месяца не прибавляется к 65000. Для 0% финансирование = 70000 — максимум дефицитов, а не сумма 70000 + 40000 + 10000.

## 7. Проверка соответствия

Требования связаны с точными именами операций и тестов в [requirements.md](requirements.md). Проверяются месячные показатели и итоги, независимость, переносы, ошибки и календарь. Фактические результаты сборки, xUnit и консольной проверки записываются в [validation.md](validation.md).
